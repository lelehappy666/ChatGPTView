# macOS 周额度自动校准与新鲜度设计规格

## 问题与证据

- 本机最新 Codex 日志记录的周额度为已用约 2%–3%，正确剩余额度为约 97%–98%。
- 使用项目当前的扫描器与汇总器完整读取同一批日志，可以得到正确结果。
- 运行中的应用仍显示 84%，该数值对应重置前的已用 16%，说明界面保留了旧内存快照，而不是百分比换算错误。
- 当前应用只依赖启动刷新、会话目录文件事件、手动刷新和刘海窗口弹出刷新。文件事件在系统休眠、跨日新建目录或长时间运行期间一旦遗漏，菜单栏没有定时自愈入口。
- 当前汇总器使用会话活动时间判断哪条额度最新。会话活动时间与额度事件时间并不等价，旧额度所在的会话后来继续活动时，理论上可能覆盖更新的额度事件。

## 目标

1. 文件监听正常时继续近实时更新额度。
2. 文件事件遗漏后，菜单栏最迟在 30 秒内自动校准到日志中的最新额度。
3. Mac 从睡眠唤醒后立即请求一次刷新。
4. 多个会话同时写入额度时，始终按额度事件自身时间选择最新主 Codex 周额度。
5. 不改变现有界面布局、菜单栏文案、日活动和项目统计结果。

## 数据新鲜度

### 额度事件时间

在 `SessionSummary` 中增加可选的周额度更新时间。`SessionScanner` 每次解析到有效的 7 天额度窗口时，同时保存该条 `token_count` 外层事件的时间戳。

同一个会话文件包含多条额度记录时，保留最后解析到的额度值和对应事件时间。旧测试数据或没有事件时间的兼容记录继续回退到会话更新时间。

### 最新额度选择

汇总仍优先使用 `limit_id == "codex"` 的主额度，避免模型专属额度覆盖主额度。在候选主额度之间，先比较周额度事件时间；只有事件时间缺失时才回退比较会话更新时间。

剩余额度继续按 `100 - used_percent` 计算，并限制在 0%–100% 范围内。

## 自动刷新

### 现有入口

以下入口全部保留：

- 应用启动立即刷新；
- 会话目录文件事件触发刷新；
- 菜单“刷新数据”；
- 刘海窗口实际弹出时刷新。

### 定时校准

应用启动后增加一个 30 秒间隔的轻量校准任务。每次只调用现有 `MonitorStore.requestRefresh()`，继续复用已有的防抖、请求合并和增量扫描缓存。

增量扫描器对未变化文件复用结果，因此定时校准主要检查文件指纹，不重复解析全部历史日志。若一次刷新仍在执行，新请求由现有逻辑合并，不并发启动第二次扫描。

应用退出时取消定时任务，防止残留任务继续持有应用对象。

### 睡眠唤醒

监听 macOS 工作区唤醒通知。收到通知后立即调用一次 `requestRefresh()`，不等待下一次 30 秒校准。应用退出时移除通知观察者。

## 错误处理

- 刷新失败时继续保留上一次有效快照，并显示现有的“数据可能已过期”状态。
- 后续文件事件、唤醒刷新、定时校准或手动刷新均可再次尝试，不需要重启应用。
- 无有效额度记录时继续显示不可用占位，不把旧额度伪装为新额度。

## 测试与验收

### 自动化测试

- 新额度事件的会话活动时间更早时，仍选择新额度事件。
- 旧额度所在会话后来继续活动时，不能覆盖新额度事件。
- `used_percent == 2` 时展示模型得到 `remainingPercent == 98`。
- 没有额度事件时间的旧记录继续按会话更新时间工作。
- 自动刷新间隔固定为 30 秒，应用启动和退出正确建立、取消刷新任务及唤醒观察。
- 现有完整 macOS 测试套件继续通过。

### 交付验收

1. 重新打包后的应用启动后显示当前日志中的真实剩余额度。
2. 保持应用运行，额度变化后文件监听正常时近实时更新；即使监听遗漏也会在 30 秒内自动纠正。
3. Mac 睡眠后唤醒，额度立即重新读取。
4. 菜单栏、五个页面、通知和 GitHub 页面行为不发生回归。
