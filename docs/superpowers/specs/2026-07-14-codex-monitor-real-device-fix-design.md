# Codex Monitor 真机修复设计

状态：用户已确认直接实现并打包查看效果。

## 目标

- 刘海窗口从 `328 × 198` 放大为 `420 × 260`，同步提高标题、正文、数字和图表字号，三页数据仍不得裁切。
- 在约 `837 MB` 的真实 `~/.codex/sessions` 数据上快速显示首屏，不再因重复全量扫描持续占用接近 100% CPU。
- 顶部菜单栏刷新操作提供明确反馈，并在刷新后显示真实项目名称和周额度。
- 周额度兼容出现在 `rate_limits.primary` 或 `rate_limits.secondary` 的 `10080` 分钟窗口。

## 数据设计

会话扫描器改为逐行流式读取，避免将大型 JSONL 整份载入内存。扫描结果按文件路径、大小和修改时间缓存；普通刷新只解析新增或变化的文件，手动刷新可强制重新检查文件元数据但仍复用未变化文件。扫描任务串行化，新的刷新请求合并到当前扫描之后，避免同时启动多个后台扫描。

每个会话同时读取顶层时间戳和 payload 时间戳，解析任务状态、Token、项目目录及周额度。周额度在 primary 与 secondary 中选择 `window_minutes == 10080` 的窗口。

## 交互设计

菜单栏刷新项在扫描期间显示“正在刷新…”，完成后短暂显示“已更新”，失败时显示“刷新失败”。刷新动作不能仅静默触发。菜单栏继续轮播真实项目名，项目为空时显示“暂无项目”而不是完全消失。

刘海窗口使用 `420 × 260`，保持顶部与刘海连成黑色区域，三页结构、横向滑动和滚轮切页不变。页面按放大后的可用空间重新布局，分页器与最底部数据至少保持 14 px 间距。

## 验证

- 单元测试覆盖 primary/secondary 周额度、流式解析、文件缓存和刷新合并。
- 布局契约测试覆盖 `420 × 260` 与底部安全间距。
- 在真实数据目录上测量首次扫描完成时间和 CPU 回落。
- 重新构建、签名、启动最终应用并确认进程常驻。
