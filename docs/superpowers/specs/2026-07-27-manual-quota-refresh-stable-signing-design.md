# macOS 手动刷新额度与稳定签名设计规格

## 背景

本次改动包含两个相关目标：

1. 将周额度页面右上角的同步状态改为可点击的手动刷新入口。
2. 修复 GitHub Token 钥匙串权限在应用更新后反复要求输入登录密码的问题。

两个目标都只修改 macOS 版本。Windows 版本、GitHub 数据展示、通知和其他统计页面保持不变。

## 已确认的问题

### 额度刷新

- 应用目前每30秒自动重新扫描 `~/.codex/sessions`，也会在目录变化、Mac唤醒和刘海窗口弹出时请求刷新。
- 周额度页面的 `等待 Codex 更新` 只是状态文字，不能直接点击。
- `MonitorStore.requestRefresh()` 已具备刷新合并、刷新状态和失败保留旧快照的能力，不需要新增额度数据源。
- 手动刷新只能立即重新扫描 Codex 写入本地的额度事件，不能直接请求 Codex 服务器。若 Codex 尚未写入新事件，刷新后仍应显示等待状态。

### 钥匙串重复授权

- 当前打包脚本使用 `codesign --sign -` 生成临时 `ad-hoc` 签名。
- 当前应用的指定要求是单次构建的 `cdhash`，没有 Team ID，也没有稳定签名身份。
- 登录钥匙串中 `com.dafeng.codexmonitor.github` 条目已经保存了6个旧版 `cdhash`，这些应用身份均已失效。
- 每次重新打包后，新的二进制产生新的 `cdhash`，钥匙串会把它当成另一个应用，因此此前选择的“始终允许”无法覆盖新包。
- 当前 Mac 没有可用的 Apple Development 或 Developer ID 代码签名证书。

根因不是 Token 保存失败，也不是应用每次删除并重建 Token，而是打包身份不稳定。

## 方案比较

### 手动刷新

#### 方案一：向页面传递刷新闭包与状态（采用）

`NotchRootView` 从 `MonitorStore` 取得 `requestRefresh` 和 `refreshState`，经 `NotchDashboardView` 传给 `WeeklyQuotaPage`。

优点：

- 页面只依赖需要的数据和动作。
- 复用现有刷新逻辑。
- 易于测试，且不会扩大页面对全局状态的依赖。

#### 方案二：页面直接观察 `MonitorStore`

实现简单，但会使展示页面依赖整个数据仓库，增加耦合，不采用。

#### 方案三：通过 `NotificationCenter` 发送刷新消息

调用关系隐藏，难以追踪和测试，不采用。

### 稳定签名

#### 方案一：本地稳定代码签名证书（采用）

在用户登录钥匙串中一次性创建仅用于本项目的本地代码签名身份，后续打包始终使用该身份。

优点：

- 不需要 Apple Developer 账号。
- 应用指定要求不再依赖每次变化的 `cdhash`。
- 适合当前本机开发、持续打包和个人测试场景。

限制：

- 证书仅存在于当前 Mac，不用于对外正式分发或公证。
- 首次建立身份及首次读取旧 Token 时，macOS 仍可能要求一次授权。

#### 方案二：Apple Development 或 Developer ID 证书

适合正式分发，但当前系统没有可用身份，且需要 Apple 开发者配置，本次不采用。打包脚本保留通过环境变量使用正式身份的能力。

#### 方案三：允许所有应用访问 Token 或改存普通文件

会降低 GitHub Token 安全性，不采用。

## 手动刷新交互

周额度页面右上角状态区域整体改为按钮，文字与图标均可点击：

- 新鲜数据：`↻ 已同步`
- 过期数据：`↻ 等待 Codex 更新`
- 没有额度：`↻ 暂不可用`
- 刷新中：转圈图标加 `正在刷新…`
- 扫描失败：`↻ 刷新失败`

交互规则：

1. 正常、过期、不可用和失败状态都允许点击。
2. 点击后立即调用 `MonitorStore.requestRefresh()`。
3. 刷新中暂时禁止重复点击；现有 Store 的合并机制继续作为第二层保护。
4. 刷新成功且出现新额度事件时，百分比与状态立即恢复。
5. 刷新成功但没有新额度事件时，继续显示 `等待 Codex 更新`，不得把旧百分比重新显示为实时值。
6. 扫描失败时保留上一次快照，按钮显示失败状态并允许重试。
7. 保留原有30秒自动刷新和5分钟额度新鲜度规则。
8. 按钮使用现有绿色状态色，增加鼠标悬停反馈，不改变页面主体布局。

## 数据与调用链

调用链如下：

`WeeklyQuotaPage` 点击按钮
→ `NotchDashboardView.onRefreshQuota`
→ `NotchRootView`
→ `MonitorStore.requestRefresh()`
→ `SessionScanner`
→ `UsageAggregator`
→ `MonitorStore.snapshot`
→ 页面重新计算额度新鲜度并更新显示。

`WeeklyQuotaPage` 接收：

- `snapshot: MonitorSnapshot`
- `refreshState: RefreshState`
- `onRefresh: () -> Void`

页面不直接持有或创建 `MonitorStore`。

## 稳定签名设计

### 本地身份

- 本地签名身份名称固定为 `Codex Monitor Local Signing`。
- 私钥和证书只写入当前用户的登录钥匙串。
- 仓库、构建目录和应用包中不得保存或提交私钥。
- 证书长期有效，避免日常版本更新导致身份变化。

### 一次性设置脚本

新增本地签名设置脚本，职责仅包括：

1. 检查同名有效代码签名身份是否已经存在。
2. 不存在时，在受限临时目录生成私钥和自签名代码签名证书。
3. 将身份导入当前用户登录钥匙串，并仅授权系统 `codesign` 使用该私钥。
4. 在当前用户范围内仅为代码签名用途信任该证书，避免扩大证书用途。
5. 无论成功或失败都清理临时私钥与证书文件。
6. 再次运行时直接复用现有身份，不重复创建。

脚本不得输出私钥、钥匙串密码或 GitHub Token。

### 打包脚本

打包脚本按以下优先级选择签名身份：

1. 环境变量 `CODE_SIGN_IDENTITY` 指定的身份。
2. 本地身份 `Codex Monitor Local Signing`。
3. 若均不存在，停止打包并给出中文设置提示；不得静默回退到 `ad-hoc` 签名。

签名后必须验证：

- 应用签名完整有效。
- `CFBundleIdentifier` 保持 `com.dafeng.codexmonitor`。
- 指定要求基于稳定证书与应用标识，不再是单独的 `cdhash`。

### 现有 Token

不修改 GitHub Token 的服务名、账号名或内容，也不删除现有钥匙串条目。

首次启动稳定签名版本时，旧条目可能再弹出一次授权窗口。用户选择“始终允许”后，钥匙串将记录稳定签名要求，后续使用同一本地身份重新打包的版本都能继续访问。

## 错误处理

- 手动刷新失败不清空额度、统计或项目数据。
- 没有新额度事件时明确保持等待状态。
- 本地签名身份创建失败时终止打包，避免生成会再次触发重复授权的临时签名包。
- 用户拒绝钥匙串访问时，GitHub 页面继续显示授权或错误提示，其他页面不受影响。
- 本地证书被删除或过期时，设置脚本重新创建身份；新的身份首次访问旧 Token 时需要重新授权一次。

## 测试

### 手动刷新

- 右上角状态区域为按钮，并且整个区域可点击。
- 点击按钮会调用传入的刷新闭包一次。
- `refreshState == .refreshing` 时显示 `正在刷新…` 并禁用按钮。
- 过期数据刷新后没有新事件时继续显示 `等待 Codex 更新`。
- 新事件到达后恢复正确百分比。
- 失败状态允许再次点击。
- 原有自动刷新和5分钟新鲜度测试继续通过。

### 稳定签名

- 打包脚本不再包含 `codesign --sign -`。
- 未找到稳定身份时打包明确失败，不生成临时签名应用。
- 找到本地身份时使用该身份完成签名。
- 连续两次打包的指定要求保持一致，且不是单独 `cdhash`。
- 应用签名、版本号和现有测试全部通过。

## 版本与交付

- 短版本从 `0.1.11` 更新为 `0.1.12`。
- 构建号从 `12` 更新为 `13`。
- 在 `main` 分支开发并使用中文提交。
- 交付重新打包的 `dist/Codex Monitor.app`。

## 验收标准

1. 周额度页面右上角无论处于已同步、等待、不可用或失败状态都可以手动刷新。
2. 刷新过程中有明确反馈，且不会重复触发并发扫描。
3. 没有新额度事件时不展示过期百分比。
4. 应用使用稳定本地身份签名，连续重新打包后指定要求不变化。
5. 首次稳定签名授权完成后，后续版本不再反复要求输入钥匙串密码。
6. GitHub Token 不离开 macOS 钥匙串，私钥不进入仓库或应用包。
7. 版本为 `0.1.12 (13)`，构建与签名验证通过。
