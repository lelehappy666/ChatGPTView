# 仅顶层会话完成提醒设计规格

## 目标

修复 macOS 与 Windows 中“内部子代理已经完成，但用户正在看的项目任务仍在运行，却提前弹出项目完成通知”的问题。完成通知只代表用户可见的顶层 Codex 会话完成，不能再由子代理、守护会话或其他内部工作会话触发。

本规格只调整完成通知资格，不改变额度、Token、每日活动、统计总览、项目状态展示与数据刷新机制。

## 已确认根因

真实日志表明，`Replaypoker(ios)` 项目的顶层会话仍处于运行状态时，内部子代理 `Epicurus` 写入了自己的 `task_complete`。当前检测器将根会话和子代理会话一视同仁，因此把子代理完成错误地解释成项目会话完成并发出了通知。随后同一顶层会话又启动了另一个内部子代理 `Boyle`，进一步证明当时用户任务并未完成。

这不是完成事件时间、刷新延迟或额度数据错误，而是通知对象的层级判断缺失。

## 已选方案

采用“只提醒顶层会话”的方案：

- 顶层会话完成时正常弹窗并播放“项目完成”音效。
- 子代理、guardian 等内部会话无论何时完成，都不产生候选通知。
- 内部会话继续参与 Token、活动热力图和统计数据，不因关闭通知而丢失用量。
- 同一项目存在多个用户可见顶层会话时，每个顶层会话仍按自己的 `session_id + turn_id` 分别判断和提醒。

不采用项目级“所有内部会话都结束才提醒”，因为内部会话可能延后写入或持续存在，会让真实顶层会话完成通知不必要地延迟。也不采用在通知中标记“子任务完成”，因为用户明确需要的是正在运行的用户会话完成提醒，而不是内部实现细节。

## 会话层级识别

扫描 `session_meta` 时解析以下字段：

- `payload.parent_thread_id`
- `payload.source`

满足任一条件即视为内部会话，不具备完成通知资格：

1. `parent_thread_id` 存在且不是空字符串；
2. `source` 是对象，且对象中包含 `subagent` 键；
3. `source` 对象任意层级的 `other` 字段值为 `guardian`。

只有没有父会话、且来源不是子代理或 guardian 的会话才是顶层会话。

为兼容旧版日志，`parent_thread_id` 和 `source` 都缺失时默认按顶层会话处理；其完成事件仍必须通过现有精确轮次与延迟复核规则，不能仅凭兼容回退直接通知。

## 数据模型

macOS 与 Windows 的会话汇总模型增加一个只读语义字段 `isTopLevel`：

- JSONL 扫描层负责依据 `session_meta` 计算该字段；
- 聚合层原样保留该字段；
- 完成检测器只接收或筛选 `isTopLevel == true` 的会话；
- 额度与活动聚合不使用该字段过滤数据。

层级识别集中在 JSONL 解析层，通知协调器不重复解释原始 `source` 结构，避免两端出现不同判断。

## 通知数据流

1. JSONL 扫描器读取会话元数据、生命周期事件与用量数据。
2. 扫描器计算 `isTopLevel`，并生成带有 `session_id`、`turn_id`、状态、完成时间与项目名称的会话汇总。
3. 用量聚合继续处理全部会话。
4. 完成检测器先排除所有非顶层会话，再使用现有 `session_id::turn_id` 唯一键检测新的 `task_complete`。
5. 顶层完成候选继续等待 3 秒、主动刷新、再等待 1 秒，并执行最终快照复核。
6. 最终快照除原有身份、状态、轮次、时间与新鲜度条件外，还必须保持 `isTopLevel == true`；否则静默取消。
7. 通过复核后，以项目目录名称作为通知标题，播放“项目完成”音效。

## 与现有规则的关系

以下规则保持不变：

- 完成候选唯一键是 `session_id::turn_id`；
- 缺少 `turn_id` 的事件不提醒；
- 应用启动只建立历史基线，不补发旧通知；
- 同一轮次不重复提醒；
- 同一会话开始新轮次、恢复运行、报错或完成身份发生变化时，取消旧候选；
- 完成事件超过 15 秒不提醒；
- Windows 刷新请求继续使用不丢失的刷新队列；
- macOS 与 Windows 使用同一层级规则和验收标准。

本规格明确替换旧规格中的“子代理会话与根会话使用相同通知规则”。内部会话仍可显示在统计来源中，但永远不能触发完成弹窗或音效。

## 异常与兼容处理

- `source` 是字符串（例如 `vscode`）时，若没有父会话则按顶层处理。
- `source` 是对象且包含 `subagent` 时，无论子对象具体内容是什么都按内部会话处理。
- `source` 任意层级出现 `"other": "guardian"` 时按内部会话处理。
- `parent_thread_id` 只有空白字符时按缺失处理。
- 元数据字段解析失败不能中断整个目录扫描；该文件沿用兼容默认值，后续仍受精确轮次和稳定复核保护。
- 等待中的候选如果在刷新后被识别为非顶层，立即取消且不留下声音或通知。

## 测试设计

### Windows 契约检查

- 根会话：`source: "vscode"` 且无父会话，解析为顶层。
- 子代理：`source` 包含 `subagent` 且存在 `parent_thread_id`，解析为非顶层。
- guardian：内部 guardian 来源解析为非顶层。
- 兼容日志：层级字段缺失时解析为顶层。
- 顶层运行、子代理完成时不产生候选。
- 子代理完成后，顶层真正完成时只产生一个候选。
- 内部会话的 Token 与活动数据仍进入统计。
- 最终复核发现候选已非顶层时拒绝通知。

### macOS XCTest

- 覆盖与 Windows 相同的元数据解析组合。
- 覆盖“Replaypoker 顶层运行 + Epicurus 子代理完成”不提醒。
- 覆盖多个顶层会话分别完成、分别提醒。
- 覆盖内部会话仍参与用量聚合。
- 保留精确轮次、历史基线、新轮次取消、延迟复核与去重测试。

## 验收标准

1. `Replaypoker(ios)` 顶层会话仍在转圈运行时，任何内部子代理完成都不弹窗、不播放音效。
2. 该顶层会话写入真实 `task_complete`，且延迟复核后仍处于同一完成轮次时，准确弹出一次以 `Replaypoker(ios)` 为标题的通知。
3. 同一项目的多个顶层会话互不干扰；哪个顶层会话完成，就提醒哪个会话。
4. 子代理与 guardian 永远不触发完成通知，但其 Token、每日活动和统计数据不丢失。
5. macOS 与 Windows 的层级识别、候选检测与最终复核行为一致。
6. 两端自动化测试、Release 构建与打包通过；macOS 新包完成签名并重启验证。

## 交付范围

- macOS JSONL 元数据解析、会话模型、完成检测与测试。
- Windows JSONL 元数据解析、会话模型、完成检测与契约检查。
- 两端构建与打包。
- macOS 应用替换、签名和重启。

不修改界面布局、额度计算、刷新频率、通知文案和声音资源。
